# Authentication, sessions and email

Run `pnpm build`, `pnpm infra:up`, `pnpm db:migrate`, then `pnpm dev`. Migration `001_auth` explicitly creates strict collection validators, unique email/username/session-token/auth-token indexes, active-session and email-lease indexes, and expiry cleanup TTLs. It is safe to rerun; it never drops existing collections/indexes. API auth handlers require its durable marker. TTL is cleanup only: every session/token lookup filters expiry and revocation. Do not point tests/seed at production.

Same-origin browser mutations require exact `WEB_ORIGIN`, JSON (DELETE may have no body), and a session-specific `X-CSRF-Token` for authenticated actions. Login/registration/reset/verify do not derive authority from a previous session and still require trusted Origin/JSON. CSRF is returned only through same-origin auth session JSON and kept in Query memory; session cookie is opaque, HttpOnly, SameSite=Lax and Secure with `__Host-` prefix in HTTPS config. Local HTTP is the explicit non-Secure exception. Sender/role IDs are never accepted. Future gateway must consume the shared authoritative auth policy and check origin before any subscription.

Initial rate limits: 60 security mutations/IP/minute, 10 login attempts/email/15 minutes, 5 reset requests/email/hour. Keys are hashed and expire in Redis; atomic INCR+EXPIRE Lua. Input has bounded length/body size. Redis commands have 3s default deadlines and bounded queues; mutations fail closed when limits cannot be enforced. Reads still authenticate through Mongo. Redis reconnection is attempted through one shared bounded connect promise. Default `trustProxy=false` avoids forged forwarded IPs; production edge requires a reviewed trusted-proxy CIDR configuration in Phase 08. Shared NATs may reach initial limits. Do not disable rate limits to fix an outage.

Argon2id default 64 MiB, time cost 3, parallelism 1, maximum two in-flight hashes per API process (excess returns unavailable rather than an unbounded queue). Wrong/nonexistent-account login verifies an actual dummy hash. Passwords are never trimmed/logged and are 12–128 characters on creation/change. Production rejects sub-minimum hash parameters, unsafe secrets and unencrypted email transport. Rerun `pnpm auth:benchmark` on deployment hardware and budget concurrency across all instances; local measurements are not auth throughput claims.

User/session real write guards in Mongo transactions serialize login quota, rotation, profile writes, revoke, reset and password changes. Password hash verified outside transaction is compared again inside its guarded mutation. Reset/password change revoke all sessions and increment authVersion; verification/reset tokens are single-use with authVersion checks. Read-only requests already overlapping a revocation may complete under their earlier authorization read; subsequent checks reject revoked sessions. Fast Redis hints do not prove delivery; Mongo is authority. Gateway hint consumption/disconnection is required in Phase 04. Unverified accounts can use profile/session settings; `requireVerified` gates future messaging/calls, `requireModerator` also gates privileged roles. No moderator accounts are seeded.

Email jobs and hashed auth tokens commit with their related mutation. Queued SMTP payloads include the one-use link and are encrypted with a **dedicated** AES-256-GCM key derived from `AUTH_EMAIL_KEY`; credentials are never logged. Jobs have CAS owner leases (30s), bounded exponential retry+jitter (up to five attempts), crash-lease reclaim, expiry and terminal dead state. Provider acceptance precedes completion; sent/dead payloads are cleared. A crash after SMTP acceptance before Mongo marking may duplicate email; fixed Message-ID is not a provider idempotency guarantee. Earlier links invalidated by a later request may still arrive—use the newest requested email. Reset/verify effect itself is deduplicated by one-use token transaction. No Rabbit atomicity is claimed for this Phase 01 Mongo job path; Phase 03 will add broker/outbox projections.

On delayed mail: confirm worker running, schema migration applied, Mailpit ready, SMTP endpoint/config valid, and `authEmailJobs` pending/sending counts/oldest age/expired leases with authorized internal inspection. Never print decrypted payloads or provider errors. Scanner/media work is unrelated to this queue. For exhausted/expired jobs, ask for a new link through the UI; do not replay a dead payload whose token expired. Controlled administrative replay/metrics/retention tooling remains Phase 08/06; there is no public replay endpoint. Completed auth-job metadata currently remains until Phase 06 retention; queued payload expires after token's 30-minute validity.

Rotate `AUTH_EMAIL_KEY` only after draining its pending jobs or keeping the old key in a planned keyring; changing it immediately makes old jobs undecryptable. Deploy CSRF/session-secret rotation coherently across instances; refresh clients for new CSRF. Durable session token hashes themselves are not signed by that secret; use revoke-all/authVersion to invalidate sessions. SMTP TLS/auth/from credentials are explicit production secrets; local Mailpit accepts only development messages. Hosted provider TLS/delivery/quotas are not validated here.

Ambiguous authentication transaction timeout may leave an inaccessible newly-created session until expiry if commit succeeded before cookie delivery; supported driver commit retries are bounded, and active-session management/reset can reconcile/revoke account sessions. No exactly-once session creation or SMTP delivery claim. Full outage, key-rotation, mixed-version and production-topology drills are later gates.

Verification commands: `pnpm test`, `pnpm test:foundation:http`, `pnpm test:integration:auth`, `pnpm test:e2e:auth`. Browser suite uses its own API/worker/Vite and unique `chat_e2e_auth_*` database. Unit/domain tests do not substitute for these integration gates.
