# Durable sends, outbox and broker operations

Phase 03 provides durable REST text/reply acceptance, an outbox relay, independent fanout/notification reference projections, and bounded broker retry/dead-letter handling. Socket delivery/offline recovery are Phase 04; notification sending/consent are Phase 06. An accepted message is committed to MongoDB. It does not assert delivery, reading or a live socket connection.

## Starting and using messaging

Build, start the existing local dependencies and run `pnpm db:migrate`. The explicit runner now applies additive `003_messaging` after 001/002. Start `pnpm dev`, register/verify through Mailpit, open `/chat`, and send text or choose **Reply** on a visible message. Attachments and calls remain unavailable. History polls every five seconds; inbox/detail every ten. The browser retains drafts and retry commands only in the current page. Refreshing, switching conversations or losing membership can discard them. Durable IndexedDB/offline sends are not implemented yet.

The composer keeps its original command UUID, text and reply across an interrupted request. Retry uses those same fields. A confirmed acceptance clears the draft. Check history before discarding an unconfirmed attempt: it may already be stored. An HTTP/network error does not prove that a transaction failed. No credentials are stored in browser storage.

`POST /api/v1/messages` accepts the strict version-1 send contract: conversation ID, client message UUID, text, optional reply target and attachment ID array. Identity is derived from the session; injected identity fields fail validation. Exact Origin/JSON/CSRF and existing auth mutation rate limits apply. Verified active membership, conversation guards and direct pair block guards are checked within the transaction, including retries. Removed/blocked users cannot use duplicate command IDs to bypass current authorization.

Raw text has a 4,000-code-point hard contract limit; the normalized text is checked against `MAX_MESSAGE_CODEPOINTS` too. NFC and CRLF-to-LF normalization precede the canonical digest. Digest includes version, conversation, normalized text, reply ID/null and attachment array. Attachments currently reject explicitly. Replies require an undeleted message from the same conversation inside a legitimate caller visibility interval. Unknown/foreign/invisible targets fail closed.

Message, ordered Long event, reference-only outbox, per-user inbox hints and command result commit under primary snapshot/majority+journal before returning accepted. The unique `(conversation,sender,clientMessageId)` command stores original digest and stable message/event/sequence references separately from editable message text. Same content returns the original reference; changed content conflicts. The acceptance result has no retained original body and never says delivered/read. Concurrent transactions and command retries remain bounded by the existing 10-second transaction deadline.

## Migration and admission

Quiesce all pre-003 API/worker writers before this upgrade. The explicit migration lease prevents concurrent migration runners, but cannot make an old application obey the new admission guard. There is no tested rolling-upgrade compatibility claim until Phase 08. Applied 001/002/003 migrations return without replacing a later validator. 003 adds optional `replyToId` to the existing message validator, preserving existing records/pending control outbox rows; it does not rewrite historical events.

Every upgraded event writer takes a real write on `outboxAdmission/global`, then counts indexed pending/claimed rows within the transaction, capped at `MAX_PENDING_OUTBOX` (default 100,000). Publication completion takes the same guard before changing status to published. There is no drifting backfilled counter: completion releases capacity through status itself. Simultaneous independent writers cannot pass an earlier count under that shared guard. Existing backlog above a newly lowered limit drains but rejects new event writes until below the limit. All processes must use consistent limits. This global contention is a deliberate initial tradeoff, not a throughput claim.

Each subscription also serializes admission to pending local projection jobs, capped at `MAX_PENDING_PROJECTIONS` (default 100,000 per subscription). Its effect marker and job roll back together on overflow. Fanout jobs await Phase 04, and notification jobs await Phase 06; they are real durable intents, not claimed socket/provider effects. Do not silently delete them to free capacity. Event/effect/command/completed-outbox retention has not yet been implemented; there is no TTL on unpublished work or effect markers. Disk monitoring, retention and benchmarked resource budgets remain later operational gates.

## Publication and consumers

Broker namespace is `${BROKER_NAMESPACE}.${MONGODB_DATABASE}`, isolating databases and test runs. The worker declares durable fanout, retry, resume and dead exchanges; independent `fanout` and `notification` quorum subscriptions; per-subscription TTL retry queues and DLQs. Local Rabbit is one node and proves no replicated availability. Production identities must receive only their scoped vhost/exchange/queue permissions; deployment/IAM drills remain Phase 08.

The relay claims one pending/due or expired-lease row with server time, a 30-second lease and a unique claim owner. It hydrates and validates an immutable event reference, publishes persistent/mandatory with a five-second confirm deadline, and only then marks published under the admission guard and unexpired owner CAS. Failed/ambiguous confirms keep admission occupied and return work to bounded exponential/jittered retry (up to 60 seconds; unpublished work has no final TTL). A crash after confirm before marking can publish twice. Expired owners cannot mark another owner's claim. Missing/corrupt canonical events stay pending with failure/oldest-age metrics and require investigation, not blind deletion.

Broker envelopes contain only version, stable event ID, conversation ID, exact string sequence and supported kind. No message bodies, cookies, email addresses or signed URLs enter this path. Consumers validate the envelope against the canonical database event and reject unsupported versions, forged references, oversized payloads and events older than the effect horizon. Each subscription transaction inserts its unique effect marker and local reference job together, then ACKs. Duplicate deliveries produce no second tested local job. Consumers use prefetch `min(BROKER_PREFETCH, JOB_CONCURRENCY)` per subscription, initially 4 each; total in-flight application deliveries can be twice that. Publisher pending promises cap at 256, messages at `MAX_SOCKET_BYTES` and confirm timeout closes an unusable transport. Connection heartbeat is ten seconds; a dead connection is detected/rebuilt independently of HTTP acceptance.

Temporary effect failures publish to that subscription's next retry queue, wait for confirm, then ACK the original. Defaults: five retries after the initial attempt, TTL 1/2/4/8/16 seconds (bounded 60 seconds). `BROKER_RETRY_BASE_MS` and attempt count are validated. Exhausted or permanent failures publish to the DLQ with classification and attempt headers before ACK. If handoff fails, the original remains unacknowledged and connection recovery redelivers it. Native quorum delivery-limit 20 is an additional repeated-disconnect safety net. Source/retry queues use at-least-once dead-letter strategy with `reject-publish`; do not change them to drop-head or at-most-once to clear pressure.

`BROKER_QUEUE_LIMIT` defaults to 100,000 per queue, with reject-publish overflow. Quorum queue length is a backpressure threshold, not an exact hard count: in-flight overshoot is documented by [RabbitMQ quorum queue limits](https://www.rabbitmq.com/docs/quorum-queues#length-limit). The local pressure test waits for an actual NACK and proves pending retention and recovery, rather than assuming immediate rejection at max+1. Publisher confirms and consumer ACKs cover different boundaries; see [RabbitMQ acknowledgements and confirms](https://www.rabbitmq.com/docs/confirms) and the [official amqplib channel API](https://amqp-node.github.io/amqplib/channel_api.html). Production cluster failover, partition safety and resource-alarm drills remain unverified.

## Incident and DLQ replay

Mongo unavailable: durable commands fail closed; do not return success. Redis unavailable: existing auth mutation limit fails closed; history authorization remains Mongo-backed. Rabbit unavailable/full/unroutable: accepted Mongo work remains pending up to the strict outbox admission cap; publication retries after recovery. Projection limit/fault: consumers retry then preserve exhausted work in their DLQ. Inspect classification, repair the dependency/schema/capacity issue, then replay a small authorized batch. A full DLQ can backpressure its source; it must not cause automatic payload dropping.

Worker `/health/live` remains liveness. `/health/ready` reports phase `messaging` and requires initialized messaging schema, a working broker runtime and a successful Mongo health check. It does not claim attachment/notification-provider/gateway readiness. `/metrics` adds `chat_outbox_pending`, `chat_outbox_oldest_age_seconds`, publication/failure totals and consumer effect/duplicate/retry/dead-letter totals. Counters are process-local and reset on restart; gauges read current Mongo state. Do not expose local metrics at a public edge. Full alerts/dashboard/tracing are Phase 08.

The replay CLI requires an existing verified moderator session in secret process environment `REPLAY_SESSION_TOKEN`; never pass tokens in command arguments or paste them into logs. Ordinary development fixtures are not moderators and there is no privileged default seed. After fixing the cause:

```text
pnpm ops:replay-dlq fanout 1
pnpm ops:replay-dlq notification 1
```

Each invocation permits 1–20 messages, checks current moderator privilege even for an empty queue, validates canonical reference and age within `EFFECT_RETENTION_DAYS`, writes `dlq.replay_requested.<subscription>` audit before handoff, confirms the targeted republish and only then ACKs the DLQ message. It does not edit payloads, fan out replay to the other subscription, or permit old/untrusted envelopes. Failure leaves the original unacknowledged/requeued; a pre-publish audit records an attempted replay, not provider delivery. A confirm-before-DLQ-ACK crash can duplicate a handoff, so retained markers still apply. A malformed head item stops this bounded CLI; broader inspected quarantine/moderation tooling remains Phase 06. Never clear dedup records to force an old replay.

Account email/invitation maintenance runs independently of broker reconnect backoff, so broker trouble does not gate SMTP processing. Worker reconnect uses bounded exponential backoff with jitter, retains durable work, cancels consumers and waits for in-flight work before closing on shutdown. Shutdown interrupts sleep and has a ten-second process deadline; abandoned leases recover rather than acknowledge uncommitted work. Full process-drain timing and dependency fault matrix remain Phase 08. Application/server clock skew and regional restore are not covered by these local tests.

## Verification

Run `pnpm test:integration:messaging`, `pnpm test:failure:outbox`, and `pnpm test:e2e:messaging` after a build and baseline startup. The outbox suite briefly stops/restarts local Rabbit in a finally block; run it sequentially with other broker/browser suites, never against a shared production broker. It uses isolated databases/queue namespaces and a test-only child process exiting after confirm. Retry/schema/capacity faults are test fixtures, not production request flags. Browser tests use real registrations, Mailpit verification and independent contexts. Their teardown removes the test DB marker before deleting the isolated broker topology so the worker cannot redeclare it. Old interrupted runs may require scoped test cleanup; never delete unrelated queue prefixes or development volumes.
