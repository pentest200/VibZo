# Notifications, reports, deletion and retention

Apply `pnpm db:migrate` before starting the API/worker on this release. Migration 006 is additive and idempotent; 001–005 are unchanged. Run `pnpm build`, `pnpm test:integration:safety`, and `pnpm test:e2e:safety` against the existing local services plus scanner. Tests create isolated synthetic databases, broker namespaces and object prefixes. They must not point at production. The default push provider is disabled.

## Push consent and delivery

`pnpm push:configure` creates **ignored** `.cache/push.env` exclusively, without printing secrets or replacing an existing identity. Load its values explicitly into both API and worker processes; these processes do not automatically source that file. Set a real `VAPID_SUBJECT` contact before enabling public delivery. Keep VAPID/private subscription encryption keys out of browser builds, logs and commits. Production enabled push rejects the local encryption default. Browser receives only the public VAPID key. New dependency: `web-push` 3.6.7 (MPL-2.0), `@types/web-push` 3.6.4; exact lockfile versions.

Only the account's **Enable notifications on this device** button calls `Notification.requestPermission`, registers `/notifications-sw.js` and subscribes with `userVisibleOnly`. No prompt/subscription on page load, no cached private API responses, and no automatic renewal after permission revocation. Server registration requires verified session+CSRF+origin. One device subscription per session, up to 10/account, bounded to 30 days and provider expiry; revoked/expired sessions cannot send. Re-enable explicitly to renew. An expired same-user session can relinquish its old endpoint; endpoint knowledge never transfers another account's subscription. Disable device registration, pause all account notifications, or revoke sessions. Pausing does not discard unread conversations.

Encrypted subscription material is AES-GCM sealed under `PUSH_ENCRYPTION_KEY`, with a unique endpoint hash for ownership. Only HTTPS default-port endpoints at exact `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com` are accepted. Canonicalize before transport; no custom endpoint or loopback exception in the production adapter. Additional browser vendors need a reviewed explicit provider addition. A closed provider list limits supported providers; it is not a universal browser support claim.

Existing Rabbit notification consumer atomically records effect+Mongo intent. A separate worker atomically expands that intent into deterministic event/device jobs under global projection admission, then marks expansion published. Rollback leaves the intent pending and no partial jobs. Expansion and **every send attempt** revalidate active verified recipient/sender, current membership and visibility interval, direct/group pair blocks, message existence/deletion, preferences, device expiry, current session/auth version. Expire intents/jobs after five minutes. Provider work uses unique server-time 30-second leases, max five attempts with bounded backoff. Gone (404/410) subscriptions are removed only if they are the attempted encrypted revision; permanent errors/exhaustion remain inspectable. The worker does not log provider error bodies/endpoints or notification content.

Payload is fixed `{"v":1,"kind":"inbox"}`. Notice text is generic and the click destination is fixed `/chat`, where current session/membership and inbox history must be fetched. No names, message bodies, conversation IDs, download URLs or credentials are sent in payloads. Provider acceptance means accepted by provider, **not displayed, delivered or read**. External push has no exactly-once idempotency guarantee: acceptance followed by timeout/crash can duplicate a generic notice. A stable per-device topic and browser notification tag coalesce when supported, without proving exactly-once delivery. Revocation cannot recall a send already authorized before the revocation committed, nor an existing OS notice. Provider requests time out at five seconds with a five-minute provider TTL. Generic old notices may remain visible; they never authorize reads.

Denied permission, unsupported browsers, missing VAPID configuration, expired endpoints and provider outages retain the real in-app unread inbox as fallback. Public push acceptance/display and native positive subscription remain separate environment-dependent verification gates; the local positive browser test fixtures permission and provider enrollment explicitly, while registering the actual service worker and persisting through the real API. Deterministic integration providers do not certify FCM/Mozilla/Apple delivery.

Official API references checked 2026-10-17: [PushManager.subscribe](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe), [showNotification](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/showNotification), [notificationclick](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/notificationclick_event), [web-push API](https://github.com/web-push-libs/web-push). Notifications require supported secure contexts and user consent.

## Reporting and moderation

Active verified members may report a visible message or current conversation, including a blocked direct conversation they can still lawfully read. Removed members, prejoin messages, invented/foreign conversation/message references fail closed. Categories are spam, harassment, unsafe, other. No free-form report text or message-body copy; reporter UUID and category/reference are restricted backend metadata. Daily rolling admission defaults to 20/account; request-level rate limits still apply. Report command IDs bind original input and retry idempotently after current authorization.

Account page displays the queue only for a verified moderator; all backend queue reads/decisions independently require that current role. There is no user-facing promotion endpoint. Provision moderators using trusted database administration and your deployment's privileged-access process; tests promote only synthetic fixtures in an isolated test database. Moderators see a reference/category, never arbitrary private message bodies. This intentionally limited workflow can dismiss a conversation/message report or remove the reported message; it does not allow conversation-wide browsing. Queue access and decisions append audit events. Repeated same decisions are idempotent; conflicting decisions fail. Removal atomically scrubs body/reactions, stages files for physical cleanup, invalidates captured conversation snapshots and appends normal deletion event/outbox. This is minimal reference review; richer evidence review requires a separately designed, audited policy.

## Account deletion

Deletion requires password, literal `DELETE`, origin/CSRF and the currently valid session. The request transaction immediately anonymizes profile/identity fields with unguessable valid tombstone identifiers, increments auth version, revokes **all** sessions, removes device subscriptions/preferences/tokens and clears encrypted pending email payloads. It queues a durable account job and appends audit. The response clears the session cookie. Username/email can be registered anew under a new UUID. A request already past an external email/push authorization point can still finish; issued verification tokens cannot authenticate a deleted UUID. Do not promise recall of external email or OS notifications.

Policy applies equally to direct and group messages: scrub the deleting user's authored bodies, reactions and associated files; keep message/command/event identifiers and original digests as pseudonymous tombstones, and preserve other members' authored messages. Group title and other members' content may still mention the deleted person; this workflow does not infer or redact third-party references. Transfer group ownership to the earliest active remaining member, using UUID as a deterministic tie-breaker; skip deleting accounts. Archive a group with no eligible successor and remove outstanding invitations. Close the deleting user's membership visibility intervals and notify surviving members. Direct history still available to the other participant, but no new sends/download grants against the deleted account.

Cleanup is bounded/restartable, using server-time unique leases and transactions with job completion fenced against the live lease. Successful batches reset failure attempts; dependency failures back off, max five consecutive failures, then keep `failed` for inspection/operator retry. Purge sessions, tokens, encrypted email jobs, push jobs/subscriptions, receipts, own reactions, captured snapshots in bounded batches. New browser authorization returning 401 clears IndexedDB, while account changes broadcast to same-origin tabs. Online peers recover durable deletion events; offline devices/downloaded copies cannot be remotely erased. A signed GET already authorized can remain usable for up to its 60-second grant, unless the object is physically removed sooner.

Physical file deletion uses the existing attachment worker. A file marked deleting cannot get new grants or attach to messages. Wait through the original signed upload deadline **plus safety grace** and any live scanner lease before removing source/approved objects and settling quota exactly once. A storage error must not free bytes or finish account cleanup. Used attachment `expiresAt` is a staging deadline, never a live attachment retention rule. Keep attachment metadata/jobs after cleanup so the independent rotating orphan reconciliation can remove crash/late-request objects; account-job completion means tracked live files/credentials/projections are gone, not proof that a global object inventory has been exhaustively scanned. Old approved candidate keys and physical orphan accounting remain the Phase 05 documented boundary. Never TTL attachment metadata as a shortcut.

Reports and audit rows keep restricted pseudonymous identifiers/category/decisions for abuse accountability, without copied bodies/PII. Content command digests, message tombstones, membership/visibility and attachment cleanup metadata remain indefinitely in this release to prevent stale-ID resurrection and preserve replay authorization. This is deliberate conservative retention, not a claim of complete anonymization or compliance certification. Finite archival/metadata compaction needs a bounded client retry/replay protocol and Phase 08 restore design.

## Configurable retention and recovery

`CONTENT_RETENTION_DAYS=0` defaults to unlimited authored content. A positive value scrubs aged message bodies through the same guarded deletion transaction and stages associated files for the attachment worker. It does not use used-file staging expiry to delete live files. `EVENT_RETENTION_DAYS` defaults to 90: advance a **contiguous prefix** replay floor and invalidate captured snapshots, forcing old conversation/inbox cursors to an authoritative consistent snapshot. Inbox hints can then be removed atomically with their floor.

Canonical conversation events remain through max(event, effect, completed outbox) retention (default 180 days). Only published outbox rows whose actual publication age exceeds that horizon, completed fanout/notification projections, terminal push jobs and aged effects may be physically pruned with the canonical event. Unpublished outbox and pending projections have no TTL and are retained. Reject expired DLQ replay using the same effect horizon; preserving dedup tombstones prevents repeated commands from reapplying. Rotating scans are bounded and eventually progress while workers are healthy; these are product policies, not throughput measurements. Late publication or delayed projection can extend physical retention beyond the configured minimum. Permanent tombstones/command records are intentionally not compacted.

`pnpm ops:safety inspect` shows bounded oldest pending/claimed/failed job IDs, states, attempts and sanitized outcomes. After repairing a dependency, `pnpm ops:safety retry-deletion <account-UUID>` resets only a failed job whose user is still deleting. Never retry sent/expired push notices in bulk. Current worker `/metrics` and existing outbox/attachment metrics remain available; comprehensive notification/deletion alerting and capacity budgets are Phase 08 work.

Mongo unavailable: safety writes/claims fail closed; committed jobs remain durable. Redis unavailable: authenticated mutations rate-limit fail closed; no provider-send authorization is inferred from Redis. Rabbit unavailable: accepted messages retain outbox; notification expansion waits. Push unavailable: bounded retry/failed inspection plus unread fallback. Scanner/storage unavailable: no new approval; deletion waits, quota remains reserved. Browser storage unavailable: existing sync fallback warns of memory-only commands, and no background push is claimed. Backups, application logs and provider-retained mail/notifications are outside live-store erasure: Phase 08 must define backup expiry, restricted restore and reapply deletion ledgers before serving restored data. No backup purge/restore or production privacy certification is claimed here.


Phase 07 adds media cleanup to account completion: a deleting account waits for deletion of any room incarnation for which it was granted credentials. A LiveKit outage retains pending completion rather than claiming media access ended. See the calling runbook for token-refresh/incarnation and delayed-revocation boundaries.
