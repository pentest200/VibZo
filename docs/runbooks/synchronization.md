# Live transport and browser recovery

Phase 04 extends durable messaging; acceptance is still Mongo commit, not a socket write. Run API, gateway, worker and Vite together with `pnpm dev` after `pnpm build`, baseline `pnpm infra:up`, and explicit `pnpm db:migrate`. The additive `004_sync` migration preserves applied 001/002/003. Quiesce pre-004 writers for that historical upgrade. The later ordinary-database schema-007 to additive-008 overlap is tested in [upgrade](upgrade.md); other release combinations require their own compatibility gate.

## Transport and authority

Gateway 3001 serves WebSocket-only Socket.IO. Vite proxies `/socket.io` including upgrades. Production needs a same-origin HTTPS/WSS edge permitting upgrades and idle timeouts longer than the 10s ping/10s timeout. There is no polling fallback, so environments blocking WebSockets use REST recovery and show reconnecting. Restrict health/metrics to operators at the production edge.

Handshake requires exact configured Origin, a current verified cookie session, and session-bound CSRF in the handshake body. No credentials in socket URLs, IndexedDB or BroadcastChannel. Commands/subscription/presence/typing recheck shared domain authority. Distributed Redis server-time connection leases enforce four sockets per session, renewed at most every 10s, expire at 60s. Each gateway admits at most 32 concurrent handshakes and 1,000 connections. Each socket permits at most four protected commands in flight; subscribe/typing/presence have separate session-scoped Redis rate budgets, applied before database work. These are limits, not measured capacities. Session authority is rechecked every `min(10, SESSION_RECHECK_SECONDS)` seconds, with command-time checks and revocation PubSub hints. Critical Redis/Mongo errors fail closed. A read already overlapping revocation can complete under its earlier transaction authority.

Rabbit fanout consumers write local reference jobs after the existing transactional effect marker. The independently scheduled worker claims each pending/expired job with a unique 30s Mongo server-time lease, publishes a body-free canonical reference to a database-scoped Redis channel, then CAS-marks completion. Publish-before-mark can duplicate; publication with zero subscribers can lose a hint. Published jobs release projection admission but are retained. Notification jobs remain for Phase 06; this worker does not send chat provider notifications.

Each gateway races a five-second Redis dispatch key; a winner dispatches locally and through the real Socket.IO Redis adapter to other gateways. Each receiver validates the canonical Mongo event and current recipient entitlement before sending a generic inbox or conversation invalidation. Membership alone never authorizes sending message bodies. Removal invalidation clears a selected unauthorized subscription; periodic authoritative checks also clear it if the invalidation is missed. Direct blocking preserves authorized prior history and denies new writes/presence/typing; shared group history/membership is unchanged. Inbox counters are also checked during session reconciliation, covering block changes and missed publications independently of the broker. Idle invalidation delay is bounded by the configured check interval plus dependency/processing time, not an immediate cutoff guarantee.

Gateway hint queues and unacknowledged hints per socket are bounded by `MAX_LIVE_BUFFER_EVENTS` (default/max 256); a missing hint ACK times out after 5s. Overflow disconnects and requires recovery. Browser hints carry no sequence advancement or body; an ACK means buffered, never delivered. Redis commands disable offline queuing, have command deadlines, and bounded queues. Socket.IO's adapter has its own PubSub reconnect behavior; it is not a durable replay log.

## Replay and snapshots

`GET /sync/conversations/:id/events?after=&through=&limit=` returns ordered reference events, captured watermark, next scanned cursor and `hasMore`. Limit is at most 100 scanned records. Invisible positions before joining/during absence advance the scan cursor without exposing their references. All sequences are canonical decimal strings backed by BSON Long; compare using BigInt, never JavaScript Number.

`GET /sync/conversations/:id/snapshot[?before=]` captures authorized current message state and watermark in one guarded Mongo transaction. A window has at most 100 messages, versions, tombstones, current member reaction counts, receipts and an older keyset cursor. Earlier/Latest controls replace the DOM window. Older windows are memory-only and revalidate on selected-conversation synchronization; they do not advance the latest projection cursor. Large invisible-history scans and inbox unread aggregation have a 3s query budget; large-history capacity is unmeasured.

`POST /sync/snapshots` materializes an owner-bound UUID snapshot with a 120s expiry checked on every page. Mongo TTL is cleanup only. At most four live snapshots per user, serialized under the inbox guard. Conversation snapshots recheck current membership when read. An inbox snapshot captures up to the configured conversation bound (default 500, max 1,000) and its first watermark in one transaction, then serves immutable pages of 100. UI pages hold at most 50 inbox entries. Replay the inbox feed after the capture watermark; if it changed, recapture before replacing the root. The client retries capture three times and scans at most ten feed pages per attempt; continuous changes postpone replacement and retry later. Deleting a ticket releases quota; expired abandoned tickets eventually release it. Snapshot creation/release has a separate 240/IP/window rate budget; durable mutations retain the existing 60/IP/window default, plus per-user snapshot quota.

Replay floors (`conversationId` or `inbox:userId`) below which cursors are invalid yield `409 CURSOR_EXPIRED`. Expired snapshot tickets also return 409. The client resets from an authorized snapshot. The [retention worker](safety.md) advances contiguous replay floors before pruning eligible replay rows and invalidates old captured snapshots. [Restore](recovery.md) also advances floors after current-policy sanitization. There is no unbounded pinned full-history snapshot claim.

## Local storage, multiple tabs and statuses

IndexedDB `commonroom-sync-v1` stores user-scoped projections and their actual snapshot watermark in one record, one inbox root/cursor, and at most 100 pending actions per user. Keep at most ten latest conversation projections. Projection and inbox writes reject cursor regression across tabs. The engine scans at most three replay pages before taking another bounded authoritative snapshot, commits it before reporting delivery, and never advances a cursor from live hints. Active reconnect and jittered 15–20s authoritative repair run even while a socket remains connected. The inbox query independently repairs every 20s. Socket invalidations are coalesced; its buffer is bounded by the public build-time `VITE_LIVE_BUFFER_EVENTS` value (validated 1..256, default 256), with reset on overflow. Export this non-secret value before web dev/build; the browser pressure fixture uses eight to exercise the same bound without a capacity claim.

Send persists UUID and exact command before the first network attempt. Tabs atomically claim one action with a 30s IndexedDB lease; ambiguous failure retries with the same ID and backoff, and server idempotency retains the original acceptance. A closed/crashed tab can delay another tab by up to the lease plus retry delay. Credentials stay in cookies/memory. BroadcastChannel shares scoped invalidations only. No tab leader is required. Logout/account changes purge all three stores, invalidate pending writes and clear private query caches. A fresh page requires current server authorization before private views: pending actions survive reload, but this is not an offline-installable app or offline-authenticated history reader. Browser eviction and site-data deletion can lose unsent actions.

Storage denial visibly switches to memory-only pending actions and suppresses automatic durable delivery claims. A refresh can lose those actions. Text still in the unsent composer stays in that page. A terminal version/input error stays visibly failed for review/discard. Lost membership purges that conversation's cache/pending actions; blocking with retained history leaves rejected actions visible. Discard warns that an ambiguous command might already be accepted.

* Pending: locally queued; storage mode is disclosed.
* Accepted: original command committed durably. Edits/deletion do not replace its original digest/reference result.
* Delivered: at least one recipient browser reports its applied, persisted visible message window. Account-level receipt ranges merge overlapping windows; a disjoint newer window replaces the range. An older unseen message outside that range is not labelled delivered. This deliberately aggregates devices per user and keeps no unbounded device receipt history.
* Read: the recipient explicitly selects **Mark messages read**, reporting read-through progress for previously visible incoming messages up to that position. It is a user report, not attention tracking. Read/delivery upper positions never regress under concurrent devices. Current membership visibility excludes receipt attribution before the current join interval.
* Unread: visible, undeleted incoming messages after the user's read cursor. Own sends, edit events, reactions and receipt events do not increase the count. Counts display `1000+` at the bounded display cap; this is not an event count.

All edits/deletes/reactions/receipts use shared membership/pair guards and atomically write their state, command result, ordered event, inbox and outbox. Edits/deletes require sender ownership and exact message version. Deletes retain tombstones and replay events. Six reaction types are accepted by the API; the initial UI exposes Like. Old visible history is rehydrated with current authorized state, including offline edits/deletion.

Typing is disposable, rate-limited, current-authorized, block-aware and expires in the browser after 4s. Presence uses separate socket/device entries with Redis server-time 30s TTL and 10s heartbeats; query checks shared conversation, target privacy and pair blocks. It shows approximate recent activity, not guaranteed online status; no last-seen history is stored. Missing/hidden presence is unknown. Multiple device entries aggregate via the expiring set.

## Diagnostics and validation

Gateway readiness requires Mongo, 004 and all three Redis clients; liveness remains separate. Worker messaging readiness additionally requires its live Redis connection. Gateway metrics include connections, queued hints and pending ACKs; worker metrics add live Redis readiness and pending/claimed fanout job count. Existing durable outbox/consumer metrics remain. These are local diagnostic signals, not measured delivery SLOs or a complete alerting system.

Run `pnpm test:integration:sync`, `pnpm test:failure:gateway`, `pnpm test:e2e:sync` after building and starting dependencies. The browser suite starts API/gateway/worker/Vite on 3000/3001/3002/5173, plus a test-only real-Redis fault proxy on loopback 16380/16381. Stop an existing dev run first. Only the worker's reference PUBLISH operations can be deliberately dropped; all other proxy commands use actual Redis. The fixture refuses non-test mode and is never part of an application build. Gateway failure tests use a separate TCP fault proxy rather than stopping shared Redis. The Phase 03 broker failure regression stops/restores Rabbit and must run separately from other broker/browser suites.

If live updates lag, inspect dependency readiness, fanout/outbox backlog and oldest age, socket ACK pressure and API authorization. Keep pending work and let replay/snapshots repair; do not clear unpublished rows, effect markers or client command IDs to make metrics green. Restarted gateways reauthorize and clients recover through HTTP. [Upgrade](upgrade.md) and [recovery](recovery.md) now document their executed local supported scopes. Cluster partitions, production TLS/edge behavior, browser support beyond tested Chromium, measured capacity and regional/PITR recovery remain separate unverified boundaries.

API choices were checked against [Socket.IO Redis adapter documentation](https://socket.io/docs/v4/redis-adapter/), [server options](https://socket.io/docs/v4/server-options/), and [MDN IndexedDB transactions](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB). Redis adapter connection-state recovery is unsupported; the independent authoritative recovery path is required.
